# 自动化测试与升级流程（第 14 项）

分析基线：v0.4 本地试用版。  
目标：核心回归可重复执行；依赖版本固定；升级前备份 → 隔离演练 → 门禁通过后才发布；失败时明确停止并回滚到可用版本。

## 1. 现状能力

| 能力 | 入口 |
| --- | --- |
| 核心门禁测试 | `make test-core` / `scripts/run_tests.sh core` |
| 后端全量 / 前端 | `make test-backend` / `make test-frontend` |
| 发布门禁 | `make release-gate`（核心 + 全量 + 前端；若本机服务在跑则核对 `/api/health` schema） |
| 升级前检查 | `make pre-upgrade`（健康检查 → `backup_db.sh` → 校验 → 记录 schema） |
| 隔离升级演练 | `make upgrade-rehearsal`（恢复到 `zhixing_upgrade_rehearsal` → migrate → 门禁） |
| CI | `.github/workflows/ci.yml`（无真实密钥；SQLite + `npm ci`） |
| Schema 版本 | `backend/app/migrations.py` 中 `SCHEMA_VERSION`（当前 **14**），表 `schema_migrations` |
| 依赖固定 | `backend/requirements.txt` 精确版本；前端 `package-lock.json` + `npm ci` |

核心门禁覆盖：接口、权限/访问控制、流式并发与隐私、知识发布/维护、接待与试听链路、schema 版本。

## 2. 数据库迁移版本

- 启动时仍执行幂等的 `migrate_schema`（`create_all` + `ADD COLUMN IF 缺失` + 索引）。
- 成功后写入 `schema_migrations(version, description, applied_at)`。
- `/api/health` 与运维巡检返回 `schema_version.applied / expected / current`；落后时整体为 `degraded`，并产生 `schema_lag` 告警。
- **不支持自动降级 schema**。回滚靠「恢复升级前备份 + 切换回旧镜像/代码」。

变更 schema 时：在 `migrations.py` 增加幂等步骤，并将 `SCHEMA_VERSION` +1，在 `MIGRATION_NOTES` 写一句说明。

## 3. 推荐发布路径

```bash
# A. 离线门禁（可不依赖业务库）
make release-gate

# B. 升级前（业务库只读检查 + 备份）
make pre-upgrade
# 记下输出中的 BACKUP_FILE=...

# C. 隔离演练（不碰 zhixing 业务库）
make upgrade-rehearsal
# 或：./scripts/upgrade_rehearsal.sh "$BACKUP_FILE"

# D. 演练与门禁都通过后，再重建并切换
docker compose up -d --build

# E. 发布后确认
curl -fsS http://127.0.0.1:18080/api/health
# 期望 status 非 fail，schema_version.current == true
```

任一步失败 → **停止发布**，不要继续 build/切换流量。

## 4. 失败时回滚到可用版本

业务库在演练中不会被覆盖。若 **D 步之后** 新版本无法工作：

1. 立即停止新容器（或 `docker compose stop backend worker web`）。
2. 检出/部署**上一可用提交**的代码与镜像标签。
3. 用升级前备份恢复业务库（示例，**确认文件名无误后再执行**）：

```bash
# 危险操作：覆盖业务库 zhixing。仅在确认 BACKUP_FILE 正确且已无人写入时执行。
FILE=backups/zhixing-….dump   # 或 .enc（需 BACKUP_PASSPHRASE）
# 建议先再做一次当前坏库备份，再恢复：
./scripts/backup_db.sh
./scripts/check_backup.sh "$FILE"
docker compose exec -T db psql -U zhixing -d postgres -v ON_ERROR_STOP=1 <<SQL
SELECT pg_terminate_backend(pid) FROM pg_stat_activity
  WHERE datname = 'zhixing' AND pid <> pg_backend_pid();
DROP DATABASE zhixing;
CREATE DATABASE zhixing OWNER zhixing;
SQL
# 若 FILE 为 .enc，先解密为临时 dump 再导入（与 restore_rehearsal.sh 相同方式）
docker compose exec -T db pg_restore -U zhixing -d zhixing --no-owner --no-acl < "$FILE" || true
docker compose up -d
curl -fsS http://127.0.0.1:18080/api/health
```

4. 确认健康检查与登录后，再排查失败原因；不要在未备份时强行重试迁移。

隔离演练库清理：

```bash
docker compose exec -T db psql -U zhixing -d postgres \
  -c "DROP DATABASE IF EXISTS zhixing_upgrade_rehearsal;"
```

## 5. CI 说明

- 触发：`main` / `master` / `codex/**` 的 push，以及 pull_request。
- **禁止**在 workflow 中写入 `ADMIN_PASSWORD`、`SESSION_SECRET`、`DEEPSEEK_API_KEY`、数据库口令等真实密钥；测试凭据仅存在于 `conftest.py` 的本地临时值。
- 前端使用 `npm ci`（锁文件），后端使用 pin 过的 `requirements.txt`。
