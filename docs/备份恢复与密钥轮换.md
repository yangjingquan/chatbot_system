# 备份、恢复、密钥轮换与数据清理（v0.4 第 6 项）

本文说明本地试用版已落地的备份演练路径、联系方式密钥分离/轮换，以及联系许可撤回与留存清理。  
**RPO（可接受数据丢失窗口）与 RTO（恢复时间目标）须由机构确认后写入运维约定，本文不擅自定为正式 SLA。**

## 1. 现状能力

| 能力 | 说明 |
| --- | --- |
| PostgreSQL 物理备份 | `scripts/backup_db.sh` → `pg_dump -Fc`，可选 `BACKUP_PASSPHRASE` 再加密 |
| 备份检查 | `scripts/check_backup.sh` 校验 SHA-256 并 `pg_restore -l` |
| 隔离恢复演练 | `scripts/restore_rehearsal.sh` 恢复到独立库（默认 `zhixing_rehearsal`），不覆盖业务库 `zhixing` |
| 逻辑加密备份 | 后台 `POST /api/admin/privacy/backup` 或 `app.backup_ops`，Fernet 保护的 JSON，用于自动化自测 |
| 联系方式加密 | Fernet；优先 `CONTACT_SECRET`，未配置时回退 `SESSION_SECRET` |
| 密钥轮换 | `CONTACT_SECRET` + `CONTACT_SECRET_PREVIOUS` 双钥解密，再 `scripts/rotate_contact_secret.py` 或后台「轮换」接口重加密 |
| 联系许可撤回 | 访客话术 / 员工 `POST /api/admin/leads/{id}/withdraw-contact` / 隐私请求 |
| 删除或匿名化申请 | `POST /api/admin/privacy/requests`（kind=`anonymize`/`delete`），完成后就地匿名化 |
| 留存清理 | 企业配置留存天数；`POST /api/admin/privacy/retention/run` 清理过期访客数据 |

## 2. 定期备份建议（本机）

```bash
# 每日或每次升级前（示例）
export BACKUP_PASSPHRASE='仅保存在密码管理器中的口令'
./scripts/backup_db.sh
./scripts/check_backup.sh backups/zhixing-….dump.enc
```

异地保存（需你方执行，脚本不会外传）：

1. 将 `backups/` 下最新文件复制到另一台机器、加密 U 盘或机构对象存储。
2. **单独**保存能解密联系方式的密钥副本（`CONTACT_SECRET`，若仍回退则还有 `SESSION_SECRET`）与可选的 `BACKUP_PASSPHRASE`；不要与备份包放在同一介质的同一未加密目录。
3. 按 `retention_backup_days`（默认 90，可在后台留存策略修改）淘汰过期备份文件。

建议用 cron / launchd 调用 `backup_db.sh`；本仓库不自动安装定时任务。生产默认备份到 `/opt/chatbot/backups`，巡检只读监控同一目录。其他路径请在服务器 `.env` 配置 `PHYSICAL_BACKUP_HOST_DIR`，并在运行脚本和定时任务时以同名环境变量传入。默认 75 分钟过期阈值为调度留有余量，不保证一小时 RPO。

### 生产备份调度示例

以下示例匹配本仓库的 Jenkins 部署：项目名 `chatbot`，应用目录 `/opt/chatbot/app`。先由运维确认主机目录、Docker 权限和时区；仓库不会自动修改 crontab。首次请手动运行并核对备份和校验和：

```bash
cd /opt/chatbot/app
COMPOSE_PROJECT_NAME=chatbot COMPOSE_FILE=compose.yaml:compose.prod.yaml PHYSICAL_BACKUP_HOST_DIR=/opt/chatbot/backups ./scripts/backup_db.sh
```

例如使用每小时第 5 分钟执行的 cron（该例不自动配置备份加密口令；如启用加密，需由安全的主机任务环境提供 `BACKUP_PASSPHRASE`）：

```cron
5 * * * * cd /opt/chatbot/app && env COMPOSE_PROJECT_NAME=chatbot COMPOSE_FILE=compose.yaml:compose.prod.yaml PHYSICAL_BACKUP_HOST_DIR=/opt/chatbot/backups ./scripts/backup_db.sh >> /opt/chatbot/backups/backup.log 2>&1
```

设置后应确认实际任务有执行、告警恢复正常，再安排异地副本和定期恢复演练。`scripts/check_backup.sh` 要求对应 `.sha256` 存在且匹配；没有校验和的历史文件不会被当作已验证。监控的文件新鲜度并不能证明可恢复。

## 3. 恢复演练

```bash
COMPOSE_PROJECT_NAME=chatbot COMPOSE_FILE=compose.yaml:compose.prod.yaml ./scripts/restore_rehearsal.sh /opt/chatbot/backups/zhixing-….dump.enc zhixing_rehearsal
# 演练库必须是新库；核对记录与恢复耗时后，由管理员确认再清理。
```

恢复脚本仅允许 `zhixing_rehearsal` 或 `zhixing_rehearsal_` 前缀的合法新库，不会覆盖已有库，并在恢复失败时返回错误。

逻辑备份自测（SQLite/接口测试已覆盖）：创建备份 → 篡改或清空目标行 → 恢复 → 会话/线索/知识回到备份点。  
从旧备份恢复到在线库后，应执行已完成隐私请求的重放（接口 `reapply_privacy=true`，或代码 `reapply_completed_privacy`），避免已匿名数据被旧备份带回。

## 4. 密钥分离与轮换

1. 首次分离：生成新的 `CONTACT_SECRET`（≥32 字符），将**当前**用于加密的密钥写入 `CONTACT_SECRET_PREVIOUS`（若从未设置过 CONTACT_SECRET，则 PREVIOUS=现有 `SESSION_SECRET`），`CONTACT_SECRET`=新值。
2. `docker compose up -d --force-recreate backend worker`
3. 执行重加密：
   - `docker compose exec -T backend python -c "from app.db import engine; from app.encryption import rotate_contacts;  
     c=engine.begin(); n=rotate_contacts(c); c.commit(); print(n)"`  
   - 或管理员调用 `POST /api/admin/privacy/rotate-contacts`  
   - 或主机配置好 `DATABASE_URL` 后运行 `scripts/rotate_contact_secret.py`
4. 确认后台线索联系方式可读后，**清空** `CONTACT_SECRET_PREVIOUS`，再次重建 backend/worker。
5. **禁止**直接覆盖 `SESSION_SECRET`/`CONTACT_SECRET` 而不走上述迁移，否则历史联系方式无法解密。

`SESSION_SECRET` 仍用于访客令牌 HMAC 与后台会话；轮换会话密钥会使旧 Cookie/访客恢复凭据失效，与联系方式密钥分开处理。

## 5. 隐私请求与备份中的处理

| 请求 | 在线库行为 | 备份中 |
| --- | --- | --- |
| 撤回联系许可 | `contact_allowed=false`，取消跟进提醒 | 旧备份可能仍为可联系；恢复后需重放已完成请求 |
| 匿名化 / 删除 | 姓名/联系方式/消息等就地替换为占位；本版不做破坏外键的物理删除 | 备份保留至备份留存到期；过期备份销毁即去掉残留 |

留存天数 `0` 表示不自动清理该类数据，仍可通过隐私请求人工处理。

## 6. 机构确认项（2026-10-27）

| 项 | 确认 |
| --- | --- |
| **RPO** | **1 小时** |
| **RTO** | **1 小时** |
| 留存天数 | 采用默认：咨询 365 / 线索 730 / 审计 1095 / 备份 90 |
| `CONTACT_SECRET` | **尚未生成**；上线时再配置（≥32 字符，异地保管） |
| 备份拷离本机 | **是**——每次备份后须人工拷到异地；脚本不会自动外传 |

其余：异地介质保管人、隐私销毁书面记录仍可按机构制度补全。
