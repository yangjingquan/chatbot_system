# 故障监控与运行告警

邮件告警默认关闭。配置 SMTP 并在后台启用邮件后，独立 `alert-monitor` 周期巡检并发送邮件；Webhook 仍为预留能力。

## 1. 监控范围

| 组件 | 来源 | 说明 |
| --- | --- | --- |
| API | 进程内延迟样本 | 最近约 200 次 `/api/*` 请求的 p50/p95 |
| 数据库 | `SELECT 1` | 公开健康检查与后台巡检共用 |
| Redis | `PING` | 未配置 `REDIS_URL` 时为 `skipped`（内存限流） |
| Worker | `ops_heartbeats.worker` | worker 循环内刷新；超过约 180 秒视为过期 |
| 任务积压 | `document_jobs` | 排队数、近 1 小时失败数 |
| 模型错误 | `model_calls` | 近 1 小时错误率 / 超时次数 |
| 磁盘 | `DATA_DIR` 所在卷 | 使用率 ≥ 90% 告警 |
| 备份 | 备份目录文件 + `ops_heartbeats.backup` | 后台「检查备份」或创建逻辑备份时写入 |

## 2. 接口

- 公开：`GET /api/health`（`status` + 精简 `checks`，不含密钥）
- 后台：`GET /api/admin/ops/status`、`POST /api/admin/ops/evaluate`
- 告警：`GET /api/admin/ops/alerts`、`POST .../ack`、`POST .../resolve`
- 通知配置：`GET/PUT /api/admin/ops/notify`
- 测试邮件排队：`POST /api/admin/ops/notify/test`（须 `settings.write`，先保存并启用邮件）
- 备份校验：`POST /api/admin/ops/backup-check`

权限：查看需 `settings.read`；确认告警与改通知需 `settings.write`。

## 3. 日志脱敏

`monitoring.redact_log` 会遮蔽 Bearer/API Key/password/常见密钥形态，并复用聊天 PII 脱敏。Worker 异常打印走该函数；告警证据中的错误摘要同样脱敏。**不能保证**覆盖全部敏感内容。

## 4. 需机构确认

- [ ] SMTP 服务器、端口、TLS 方式、发件邮箱、认证账号与授权码、收件邮箱或邮件组及出站策略
- [ ] Worker 过期、任务积压、模型错误率、磁盘阈值是否符合机构运维习惯
- [ ] 备份巡检周期（主机 cron + 后台检查）与告警值班人

## 5. 本地验证建议

```bash
cd backend && python -m pytest tests/test_monitoring.py -q
docker compose up -d --build backend worker alert-monitor web
# 后台 → 运行监控：查看状态、模拟停止 worker 后等待心跳过期
```

## 6. 邮件通知配置与验收

在服务器已有 `.env` 中配置下列变量，不要提交 `.env`、密码或授权码。SMTP 授权码由邮件服务提供，并不一定是网页登录密码；含 `$` 或 `#` 的值在 Compose `.env` 中使用单引号包裹，避免被插值。默认使用 STARTTLS；465 SSL 与 587 STARTTLS 是常见组合，以邮件服务商实际配置为准。服务器证书必须通过系统 CA 和主机名校验，不支持明文发送。

```dotenv
SMTP_HOST=smtp.resend.com
SMTP_PORT=465
SMTP_SECURITY=ssl
SMTP_USERNAME=resend
SMTP_PASSWORD='填写 Resend API Key'
SMTP_FROM=alerts@nexbyte.top
SMTP_TIMEOUT_SECONDS=15
ALERT_MONITOR_INTERVAL_SECONDS=60
```

用户名与授权码必须同时填写；若服务端允许免认证的 TLS 内部中继，两项可同时留空。以上示例使用发信域名 `nexbyte.top`，该域名须先在 Resend 完成发送域名验证；API Key 属于敏感信息，实际值应由机构保存在服务器，不应提交版本库。`alert-monitor` 使用自己的 SMTP 环境变量；改动后需重建该服务。

1. 启动或更新服务：`docker compose up -d --build alert-monitor`（正式环境使用项目现有的生产 Compose 组合）。升级前先做好数据库备份，新版本自动执行 schema 16 迁移。
2. 在后台「运行监控 → 通知渠道」选择邮件，填写一个接收邮箱并启用；多人接收建议填写邮件组地址。保存后检查巡检心跳及 SMTP 参数是否填写完整。
3. 点击「发送测试邮件」，在告警列表选择「全部」或「已恢复」查看发送结果，并由收件人确认实际收到。随后模拟一次故障和恢复，核对告警、恢复邮件及处理记录。页面中的“邮件服务器已接受”不代表最终投递到收件箱。
4. 失败会记录脱敏后的原因并自动重试，间隔指数递增至最多 30 分钟；网络不稳定或进程在服务端接受邮件后崩溃时，重试可能产生重复邮件。关闭通知后不再领取新的邮件；已开始的 SMTP 发送无法撤回。

独立巡检进程不依赖打开后台页面，但自身停止、数据库不可访问或整机/网络故障时不能可靠发信；需由外部监控或邮件服务自身的监控补充。API 延迟样本是进程内数据，独立巡检不会代替 API 进程评估延迟；建议接入外部可用性与延迟监测。
